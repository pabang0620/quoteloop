# VERIFY: sandbox checks

The results written next to each item are from 2026-11-12; an item without a result is **not yet verified** against the PayPal sandbox. The code has a real call path for each item (`shared/paypal.js`, `shared/paypalSdk.js`, `supplier/vault.js`, `supplier/settle.js`, `buyer/audit.js`); the tests run the same paths against the bundled mock PayPal process, whose response shapes come from the PayPal REST documentation and the `@paypal/paypal-server-sdk` models. A person runs these with sandbox keys, in this order, and records the result next to each item.

## Set up (once)

1. Create two sandbox business accounts: **supplier** (Northbeam) and **procurement** (Brightcup). Create a third for judges if the procurement account is kept for the real-use story, and give it a large balance (`ppBalance` accepts 0 to 100000 in bulk-account creation; a single account is edited in the sandbox dashboard).
2. In the supplier's REST app: enable Accept payments, open Advanced options, and check that Vault is selected. Put its keys in `SUPPLIER_PAYPAL_CLIENT_ID` / `SUPPLIER_PAYPAL_CLIENT_SECRET`.
3. In the buyer's REST app: enable Transaction Search (scope `https://uri.paypal.com/services/reporting/search/read`). Put its keys in `BUYER_PAYPAL_CLIENT_ID` / `BUYER_PAYPAL_CLIENT_SECRET`.
4. Start the services (`npm start`; the mock process may stay up, it is only used for simulated calls past a limit). The page header should say the supplier PayPal mode is `sandbox`.

## Mock vs sandbox: shapes to compare while running the checks

These were written from documentation, not from a live response:

- setup-token `links[].rel` (`approve`), the return query parameter name (`approval_token_id`)
- payment-token `payment_source.paypal.email_address` (used to tell the judge account from others)
- Orders `purchase_units[].payments.captures[]` for a vault order, and whether a vault order is `COMPLETED` immediately
- Transaction Search event codes (`T0006` charge, `T1107` refund) and `paypal_reference_id` on the refund row
- invoice `amount.breakdown.discount.item_discount`, `detail.payment_term.term_type`

If any differ, fix `mockpaypal/state.js` and the reader in `buyer/audit.js` / `buyer/verifyDraft.js` together, then rerun `npm test`.

## Operator, during the judging period

- Daily: `POST /admin/daily-check` on the buyer service with `x-admin-token` (also runs by itself every 24 hours). The buyer agent co-signs a $1.00 check, the supplier verifies that signature, charges the saved judge account and refunds it; the buyer's audit pairs the charge with the co-signature, so it never raises an alert.
- Before filming, or when the numbers look off: `POST /admin/reset-demo` on the buyer service (token) clears every visitor's budget, deals, approvals and audit state.
- If the page shows "being topped up": top up the judge account in the sandbox dashboard, then `POST /admin/judge-balance {"cents": 1000000}`.
- Refunds run every 30 seconds in the supplier; `POST /admin/run-refunds` forces a pass.
- Before filming the PayPal activity scene, run one deal at least 3 hours earlier so it shows as matched.
